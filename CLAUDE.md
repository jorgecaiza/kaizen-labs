# 1. Brand Overview

## Brand Name

**Kaizen Labs**

The name is built around the Japanese concept **Kaizen (改善)**, commonly associated with continuous improvement.

The concept is particularly relevant to software development:

> Build → Learn → Improve → Evolve

Kaizen Labs is an Ecuadorian software company focused on developing digital products, web applications, SaaS platforms and custom software solutions.

The brand should communicate **technology, continuous improvement, engineering, innovation and reliability**.

# 36. Internationalization & Language Support

Kaizen Labs must support **Spanish and English as first-class languages** throughout the entire website.

Every piece of user-facing content must be available in both languages.

## Supported Languages

- 🇪🇸 Spanish (`es`)
- 🇺🇸 English (`en`)

Spanish should be the default language when no more specific preference can be determined.

---

## 36.1 Complete Translation Coverage

All visible text must be translatable, including but not limited to:

- Navigation
- Headers
- Hero sections
- Buttons
- CTAs
- Forms
- Form labels
- Placeholders
- Validation messages
- Error messages
- Success messages
- Notifications
- Tooltips
- Modals
- Cards
- Service descriptions
- Product descriptions
- Footer
- Legal notices
- Privacy-related text
- Accessibility labels
- Metadata where applicable
- SEO titles and descriptions
- Empty states
- Loading states
- 404 and other error pages

**No user-facing text should be hardcoded directly into components when it requires translation.**

---

## 36.2 Translation Dictionary

The application must use a centralized translation dictionary / localization system.

Example structure:

```text
/locales
├── en
│   └── common.json
└── es
    └── common.json
```

Or an equivalent structure appropriate for the selected framework.

Example:

```json
{
  "navigation": {
    "home": "Home",
    "services": "Services",
    "about": "About",
    "contact": "Contact"
  }
}
```

Spanish:

```json
{
  "navigation": {
    "home": "Inicio",
    "services": "Servicios",
    "about": "Nosotros",
    "contact": "Contacto"
  }
}
```

The exact implementation may use JSON, TypeScript objects, or an established internationalization library, but the architecture must keep translations centralized and maintainable.

---

## 36.3 Language Selector

The website must include a clearly accessible language selector.

The user must be able to manually switch between:

- **Español**
- **English**

The selector may be represented by:

- Language name
- Language code (`ES` / `EN`)
- Globe icon
- Dropdown
- Other minimal UI appropriate to the design

The language selector should be available from the main navigation or another consistently accessible location.

---

## 36.4 Automatic Language Detection

When a user visits the website for the first time, the application should determine the preferred language automatically.

The detection strategy should consider, in order:

1. Previously selected language stored by the user.
2. Browser/system language.
3. Geographic location when appropriate and reliably available.
4. Default language.

The manually selected language must take precedence over automatic detection.

### Example

If the user's browser is configured for English:

```text
User visits website
        ↓
Detect browser language
        ↓
English
        ↓
Display English
```

If the browser is configured for Spanish:

```text
User visits website
        ↓
Detect browser language
        ↓
Spanish
        ↓
Display Spanish
```

If the browser language cannot be determined or is unsupported:

```text
Unknown / unsupported language
        ↓
Default to Spanish
```

---

## 36.5 Geographic Detection

Geographic location may be used as an additional signal for the initial language selection, but it must **not override an explicit user preference**.

For example:

- User located in Ecuador + Spanish browser → Spanish
- User located in Ecuador + English browser → English
- User located in the United States + Spanish browser → Spanish
- User manually selects English → English regardless of location

Do not request precise GPS/location permissions solely to determine the language.

Prefer browser locale and other non-invasive signals whenever possible.

---

## 36.6 Persisting the User's Choice

When a user manually selects a language, that preference should be persisted.

For example:

```text
User selects English
        ↓
Save language preference
        ↓
User navigates through website
        ↓
English remains active
        ↓
User returns later
        ↓
English remains active
```

The implementation may use an appropriate mechanism such as:

- Cookie
- Local Storage
- Server-side preference
- URL locale
- Framework-supported locale persistence

The implementation should follow the architecture and framework selected for the project.

---

## 36.7 URL / Routing Strategy

If the application uses localized routes, the preferred structure is:

```text
/en/
es/
```

or:

```text
/en/services
/es/servicios
```

The final routing strategy should be compatible with SEO and the selected framework.

If localized URLs are used:

- Each language should have its own canonical URL.
- Appropriate `hreflang` metadata should be generated.
- Language alternates should be correctly declared.
- Switching languages should preserve the current page whenever a translated version exists.

Example:

```text
English:
https://example.com/en/services

Spanish:
https://example.com/es/servicios
```

---

## 36.8 SEO

Internationalization must also apply to SEO.

Each language should have appropriate:

- `<title>`
- Meta description
- Open Graph title
- Open Graph description
- Social sharing metadata
- Canonical URL
- `hreflang`
- Structured data where applicable

Search engines should be able to understand that English and Spanish are alternate versions of the same content.

---

## 36.9 Developer Requirement

Developers must avoid hardcoding user-facing strings inside UI components.

Instead of:

```typescript
<button>Contact us</button>
```

use the project's localization mechanism:

```typescript
<button>{t("contact.button")}</button>
```

This ensures that adding or modifying translations does not require changing the component itself.

---

## 36.10 Future Extensibility

Although the initial implementation only requires:

- Spanish
- English

the internationalization architecture should allow additional languages to be added in the future without requiring a major rewrite of the application.

The system should therefore treat language as configurable application data rather than hardcoding the application around only two languages.

---

## 36.11 Acceptance Criteria

The implementation will be considered complete when:

- [ ] Every user-facing text has an English translation.
- [ ] Every user-facing text has a Spanish translation.
- [ ] A visible language selector is available.
- [ ] The website can automatically detect the user's preferred language.
- [ ] Browser/system language is considered.
- [ ] Geographic location may be considered as a secondary signal.
- [ ] Manual language selection always takes precedence.
- [ ] User language preference is persisted.
- [ ] No important UI text is hardcoded outside the localization system.
- [ ] SEO metadata is translated.
- [ ] Error and validation messages are translated.
- [ ] Accessibility labels are translated.
- [ ] The architecture allows additional languages to be added later.

**The goal is not simply to translate the website. The goal is to make internationalization a fundamental part of the application's architecture from the beginning.**
